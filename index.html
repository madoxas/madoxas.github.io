Reference model

Entity relationships

The complete relationship model used by every example below. Solid purple lines from a timeline entry identify its single source; dashed amber lines identify optional references.

Tag: many properties; at most one location in total.

Property: at most one location in total.

CountrySubdivision: exactly one parent; many properties.

TimelineEntry source: exactly one supported entity in total.

TimelineEntry references: many entities of any supported type.

Supported location targets: Country or CountrySubdivision.

A3 · Select several tags or properties

“One or several” does not establish whether several values mean ANY or ALL. The same graph makes the difference visible.

Suggested default: ANY within one filter type. Keep a separate AND/OR decision for combining different filter types. Existing Segments combine different non-empty filter types with AND.

Discussion draft

Proposed baseline interpretation

A small, predictable rule set that satisfies the clearest parts of the requirements while keeping unresolved traversal rules explicit.

  1. Result rows are TimelineEntry and CountrySubdivision, not Tag, Property, or Country.
  2. A selected tag expands one hop to its HasProperty properties.
  3. A property does not expand backwards to tags or sideways to sibling properties.
  4. A tag/property filter matches an entry when its source is selected or expanded.
  5. A tag/property filter matches a subdivision having a selected or expanded property.
  6. REFERENCED_BY does not match unless an “include references” option is added.
  7. Location filters default to SELF_AND_DESCENDANTS.
  8. Location filters match subdivisions in scope and entries directly sourced by a location in scope.
  9. Location inheritance from tag/property sources remains a separately confirmed rule.
  10. Use ANY within one filter type and AND between different non-empty filter types.
  11. Return each entity once, even when several paths match it.

Before implementation

Decisions required

  • Result types: Are tags returned, or only used as filters and sources?
  • References: Does REFERENCED_BY count, or only HAS_SOURCE?
  • Reverse traversal: Does selecting a property include entries sourced by tags having it?
  • Located sources: Do entries inherit the explicit location of their tag/property source?
  • Owned properties: Does subdivision HAS_PROPERTY establish an effective property location?
  • Hierarchy scope: Which depth scopes are supported, and which is the default?
  • Multiple values: Confirm ANY within one filter type.
  • Mixed filters: Confirm AND between tag, property, and location filters.
  • Selected row: Does a selected subdivision appear even without entries or properties?
  • Deduplication: Confirm that multiple matching paths still produce one result row.

After these decisions are answered, each open row can become a required match or exclusion and the tables can be used directly as integration-test acceptance cases.
